# Task 2 — From Tables to Notebooks

**Goal:** turn the joined Olist tables from Task 1 into a real, leakage-aware ML pipeline — one notebook per job — ending with a first trained model compared against a baseline.

## What's in this folder

| File | Purpose |
|---|---|
| `01_read_and_join.ipynb` | Read every table, aggregate items/payments to order level, join into one ML table |
| `02_create_labels.ipynb` | Build the `is_late` label, sanity-check it, check class balance |
| `03_train_val_test_split.ipynb` | Split chronologically into train / validation / test, before any deep analysis |
| `04_eda.ipynb` | Detailed EDA — **training split only** |
| `05_feature_engineering.ipynb` | Build features, fit transformers on train, apply everywhere, save the fitted objects |
| `06_train_tune_evaluate.ipynb` | Baseline, tune on validation, evaluate on test exactly once |
| `artifacts/` | Everything the notebooks save — see the table below |

Each notebook reads the artifact written by the one before it and writes its own for the one after it, so they must be run **in order, 01 → 06**.

## How to run it

1. From the repo root, make sure the database from Task 1 is running and populated:
   ```bash
   docker compose up -d
   ```
2. Make sure your `.env` file is filled in (see `.env.example` at the repo root).
3. Install the extra Task 2 dependencies (already added to the shared `requirements.txt`):
   ```bash
   pip install -r requirements.txt
   ```
4. Run the six notebooks **in numeric order**, top to bottom, from a clean kernel each time:
   ```bash
   jupyter notebook tasks/task-02-tables-to-notebooks/
   ```

## Notes to self

- **Leakage rule, applied from Notebook 1 onward:** `olist_order_reviews` and `order_delivered_customer_date` never enter the feature set — they only exist after the order has already arrived. `order_delivered_carrier_date` is excluded too, since it's still a future event relative to purchase time.
- **Why a time-based split (Notebook 3):** in production the model always predicts on orders that come *after* its training data — a random split would hide that and overstate how well the model generalizes.
- **Every fitted object gets saved, not just the output table (Notebook 5):** the imputer, scaler, one-hot encoder, and the "top categories" list are all bundled and saved so a later production pipeline can load and reuse them exactly, instead of re-fitting on new data.
- **The test set is opened exactly once,** in Notebook 6, after tuning is already finished on validation.
- No production scripts yet — that's a later task. These six notebooks stay as-is, numbered and in order.
